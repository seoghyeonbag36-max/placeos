### 2-3. 재개 방식 — 3D 디지털 트윈(2026-10-27 사용자 결정)

계획상가(집합건물)는 **3D 디지털 트윈**으로 다룬다(CLAUDE.md §3D 디지털 트윈 · `docs/feature-posting.md` §0-V). 트윈이 하는 일은 셋이다.

| | 내용 |
|---|---|
| ① 실시간 공실 | 공실 건물을 실시간으로 구현한다 — 네이버 지도·거리뷰의 최신성(촬영 시점·갱신 주기)으로 표현이 안 되는 「지금 비어 있는가」 |
| ② 건물별 공실 → 지역 공실률 | 서울·경기·지방 등 공실률이 정확히 집계되지 않는 계획상가에 적용해 건물별(호실별) 공실을 세고, 실제 지역 공실률을 조사한다 |
| ③ 외부 → 내부 동선 → 도시재생 | 트윈을 바탕으로 계획상가 바깥에서 안쪽까지의 최적 이동 동선을 만들어 도시재생 관련 사업으로 확장한다 |

- 첫 대상은 위 11곳이다. 계획상가 7곳은 ②가 곧 재개 조건이다 — 일반건축물 대장 분모로는 상업 재고의 일부만 덮던 자리를 호실 단위 공실이 채운다.
  단일시설 4곳(몰 한 채가 상권)도 건물 한 채라 ①·③의 축이 맞지만, 범위에 넣을지는 사용자가 정한다.
- 구현 전이다 — 실시간 공실의 원천 · 호실 형상의 원천 · 동선 모델의 입력이 열려 있다(§0-V ⬜). 그 전까지 이 11곳은 서빙하지 않는다.
- 서울 서빙 7곳(§2-2)도 같은 질문을 가진 곳이라, 트윈이 서면 같은 축으로 다시 잴 수 있다(서빙에서 빼지 않는다).

## 3. 경기 GNN — 공통 피처판

### 3-1. 왜 공통 피처판인가

서빙 모델 `industry-gnn`(132열)에는 **서울 상권분석(TRDAR) 수요 블록 37열**이 들어 있다. 경기에는 그 소스가 없다
(`cities.has_trdar = False`). 없는 열을 0 이나 서울 평균으로 채우면 합성값이 실측처럼 들어간다 → 수요 블록을 뺀 공통 피처로
**세 도시를 함께** 학습했다.

| | 값 |
|---|---|
| 모델 | `industry-gnn-common` · 체크포인트 `ml/artifacts/industry_gnn_common.pt`(65KB) |
| 피처 104열 | 좌표 2(`dx_km`·`dy_km`) · 기본 2(`log_bld_size`·`log_knn_deg`) · **거점 원핫 90**(`d_<slug>`) · 건물 10 |
| 학습 | 서울 + 고양 + 파주 노드 95,098 · 엣지 292,058 · val 선택(top1) · test 19,023 |
| 학습 명령 | `python -m ml.training.train_gnn --cities seoul,goyang,paju --serve-cities goyang,paju --tag common`(평균표만 다시: `--predict-only`) |

⚠ **거점 원핫 90열** — 서빙 거점이 늘거나 줄면 열 수가 바뀌어 **다시 학습해야 한다**(`predict_only` 는 피처 순서가 체크포인트와
다르면 멈춘다). 다음 경기 배치를 서빙할 때 이 모델도 같이 돈다.

앞 턴 검증: 서울에서 서울 전용 피처를 빼도 서울 실력의 91% 가 남았다(+3.63 → +3.30%p, 여전히 `실력`). 「새 데이터 없이 경기에
바로 쓸 수 있다」의 근거다.

## 4. 「파주 → 고양 → 서울」 상권 흐름

### 4-1. 답하는 세 질문

창업자가 이 축에서 자리를 볼 때 — ① 세 지역 사이에 사람이 **얼마나·언제·무엇 하러** 오가나 ② 마디(파주·고양은 시군구,
서울은 상권)마다 손님이 **어디서·언제·무엇 하러** 오나 ③ 측정으로 고른 **짝(시너지 후보)** — 「이 지역 사람이 하루 N명 저
상권으로 간다」까지가 측정이고, 그 짝으로 무엇을 해 볼지는 **가설**로 적는다. 매출·성공을 약속하지 않는다.

  마디를 「전부 빌린 값」/「섞여 있다」로 밝힌다 — 고양 세 마디는 전부, 파주시는 일부(금촌만 실측).

  10-26 실측에서 네 마디 모두 같은 서울 상권(을지로 · 하루 1,608~4,596)을 가리켰다. API 에는 남아 있고, 출근은 마디 상세의
  목적 구성·시각 막대가 보여 준다. 그래서 카드는 12장(4마디 × 방문·유입·생활권)이다.
- 업종을 골랐으면 마디의 거점마다 입지 점수 순위(`fit_rank`)가 붙는다 — §3-3 과 **같은 순위**다(테스트가 고정).
- **방문·유입 카드에는 시각을 붙이지 않는다**(10-27 검증에서 발견) — 짝의 「많이 닿는 때」·평균 분은 **모든 목적 합**(출근·귀가 포함)이라,
  방문 인원 옆에 두면 귀가 시각이 방문 손님의 때로 읽혔다(예: 망원 → 파주시 카드 19·18시, 방문만 재면 중앙 14:17). 시각은 모든 목적을 세는
  생활권 카드에만 붙인다. 방문만의 시각·평일/주말은 Stream 작업에서 수집 집계부터 더한다(→ docs/finding-corridor-stream-2026-10-28.md).
- 흐름 자료가 없으면(404) 지어내지 않고 「흐름 자료가 아직 없어요」로 물러난다.

### 5-1. 본전 시점은 답하지 않는다(10-27 · 검증 중 발견)

매출 재료가 없으니 경기 9곳의 3-Tier 는 전부 계수 폴백(`rent+fitout`)으로 돌았다. 그 계수는 원가(매출비례)와 인건비가 빠져
**마진이 과대 · 회수기간이 과소**하게 나온다(`districts.COST_BASIS_LEGACY_NOTE` 가 스스로 적는다). 실측: 금촌 첫 유닛 가성비
「월 매출 2,170 · 월 비용 309 · 본전 0.9개월」(마진 86%) · 대화역 고급화 1.4개월. 창업자 흐름의 머리 문장 「… 하면 N개월이면 본전이에요」가
이 값을 그대로 말하고 있었다 — 정체성의 셋째 약속(「월 얼마고 몇 달이면 본전」)을 근거 없는 계수로 답한 것이다.

| 자리 | 바뀐 것 |
|---|---|
| `/postings` | 유닛마다 `payback_unavailable_reason` — 「{도시} 상권에는 매출 자료(서울시 상권분석 추정매출)가 없어 본전 시점을 계산하지 않아요. …」. 유닛(건축물대장 실측)과 시나리오는 그대로 싣는다(`basis` 가 폴백임을 밝힌다) |
| `/ai/simulate-revenue` | 계수 폴백 대신 `calculation_status: "unavailable"` + 같은 사유. 외부 코파일럿이 답하면 그 답은 쓴다 — 막는 것은 우리 손으로 적은 계수뿐이다 |
| 흐름 R3 · R4 · 상권 비교 | 사유가 있는 유닛은 「본전 계산」으로 세지 않는다 — 칩·배지·비교 칸이 0 이 되고, R4 는 「몇 달이면 본전인지 보기」 대신 사유와 「현장 금액으로 예산 점검」을 낸다 |
| PPPP Page 화면 · Posting 화면 | 화면은 그대로다. Page 의 유닛 카드는 회수기간 칸 대신 사유를, Posting 계산은 사유를 보인다(세부 업종 운영 입력 계산은 그대로 열려 있다) |

- **도시 단위로 재료가 없을 때만** 막는다(`cities.has_trdar` 가 False 이고 그 거점에 실측 매출 모델이 없을 때). 경기 매출 소스가 배선돼
  `posting_revenue.available` 이 참이 되면 사유는 저절로 사라진다.

  경기 9곳은 세 tier 모두, 가락·불광은 고급화만 그렇다. 위 사유(`payback_unavailable_reason`)는 「계산한 tier 가 하나도 없을 때」로 바뀌어
  경기 9곳에 그대로 걸린다 → [finding-posting-tier-availability-2026-10-28.md](finding-posting-tier-availability-2026-10-28.md)
