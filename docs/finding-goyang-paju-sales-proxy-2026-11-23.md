# 고양·파주 매출 대리값 — 확인했고, 없어서 제외한다 (2026-11-23)

> **사용자 결정(2026-11-23 ④)**: 「추정 매출 대리값은 우선 확인해보고, 없으면 제외할 것. 요구 판매량 계산을 고양·파주에 먼저 적용할 것.」
> 서울의 매출 재료는 서울시 상권분석(TRDAR) 추정매출이다. 고양·파주에 같은 자리를 채울 수 있는 소스가 있는지 **1콜·페이지 실측**으로 확인했다.
> 결론: **쓸 수 있는 대리값이 없다 → 제외.** 화면은 지금처럼 「자료 없음」을 유지하고, 그 자리를 요구 판매량이 채운다(§3).

## 1. 지역사랑상품권을 쓸 수 있다고 해도 매출 대리값은 아니다

15149767 이 서더라도 **상품권으로 결제한 금액**이다 — 점포 전체 매출이 아니고(카드·현금 제외), 상품권 사용률은 업종·연령에 따라 크게 다르다. 서울 TRDAR 와 같은 스키마(6구간·연령·성별)로
서려면 업종 구분·시간대가 있어야 하는데 페이지는 이를 밝히지 않는다. **「상품권 결제 비중」 같은 보조 관측**으로만 쓸 수 있고, 그것을 매출처럼 보이게 하지 않는다(CLAUDE.md 「합성값을 실측처럼 보이지 않는다」).

**재개 조건**(사용자 몫 — 포털 로그인이 필요하다):
1. 공공데이터포털에서 15149767 **활용신청**(키가 이미 있어도 데이터셋마다 신청이 따로다) → 마이페이지 미리보기/Swagger 로 **오퍼레이션 경로와 응답 필드**를 확인한다.
2. 응답에 **업종 필드**가 있고 `usage_rgn_cd = 41281 · 41285 · 41287 · 41480` 으로 행이 나오는지 1콜로 본다.
3. 둘 다 되면 `docs/finding-*` 로 남기고, 쓰더라도 「상품권 결제 비중」으로만 표기한다.

## 2. 하지 않은 것

- 서울 값·경기 평균·R-ONE 임대료로 **합성한 매출 추정**을 만들지 않았다. 없는 구간은 「자료 없음」으로 둔다(`inputs_source.foot = "none"` · 본전 시점 불답 — decision-goyang-paju-corridor §5).
- 낡은 카드매출(2023-12)을 「구성비 참고용」으로 쓰자는 안은 올리지 않았다 — 서울과 같은 스키마가 서기 전에는 「없음」을 유지하는 것이 현행 규칙이다.
- 경기데이터드림 차단 사유(031-8008-4114)는 사용자 문의 사항으로 그대로 남는다.

## 3. 그래서 무엇이 대신 서나 — 요구 판매량

사용자 결정 ④의 둘째 문장대로 **요구 판매량**을 고양·파주 자리 상세(`flow/screens/Space.tsx` R4)에 먼저 붙였다. **매출 추정이 필요 없다** —
`BEP 월매출 = (월세 + 기타 고정비) ÷ (1 − 변동비율)` → 하루 필요 판매량 = BEP ÷ 객단가 ÷ 영업일(`lib/menuPlan.menuBep` 그대로).
월세는 그 자리의 추정 월세(R-ONE 공유일 수 있다 — 화면이 밝힌다), **나머지 네 칸(객단가·변동비율·기타 고정비·영업일)은 기본값 없이 직접 입력**이다.
화면은 「필요한 양이지 이 상권에서 팔릴 양이 아니다」를 함께 적는다 → `flow/RequiredSales.tsx` · 가드 `RequiredSales.test.tsx`(5) · `FlowApp.test`(고양·파주 노출 · 서울 비노출).

- 범위는 `REQUIRED_SALES_CITIES = ["goyang", "paju"]` 뿐이다. 같은 사유(매출 재료 없음)의 경기 3차·광주·전주로 넓히는 것은 별도 결정이다.
- 아직 안 된 것: 서버가 업종별 참고 객단가·변동비율을 **출처와 함께** 주는 것(지금은 전부 사용자 입력 — `AreaBepPlanner` 의 seed 예시와 같은 원칙으로 가정값을 만들지 않았다).
