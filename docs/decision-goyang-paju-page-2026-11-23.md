# 고양·파주 전용 페이지(경로) — 주소로 고르는 사이트 범위 (2026-11-23)

> 사용자 요청: 「고양시와 파주시만 따로 보여주는 웹페이지 혹은 경로를 만들어줘.」 (서울 순위·서울 모델은 바꾸지 않는다 — 11-23 결정)

## 1. 어떻게 열리나

| 주소 | 하는 일 |
|---|---|
| **`placeos.co.kr/goyang-paju`** | 백엔드가 `307` 로 `/?region=goyang-paju` 에 보낸다(`app/main.goyang_paju_entry`). 해시 라우팅이라 서버가 아는 경로는 이 하나뿐이다 |
| `/?region=goyang-paju` | 앱이 고양·파주 범위로 열린다. 로컬 개발(Vite)은 이 쿼리나 경로 `/goyang-paju` 를 그대로 받는다 |
| `/?region=seoul` | 서울로 되돌린다 |
| 아무것도 안 붙인 `/` | **지금까지와 같다 — 서울만 보인다.** 서울 기본 동작은 바뀌지 않았다 |

한 번 고르면 그 **탭**(sessionStorage `placeos.scope.v1`)에서는 해시 이동으로 주소가 바뀌어도 유지된다. 새 탭·새 방문자는 기본(서울)이다.
범위는 모듈이 불릴 때 **한 번** 정해진다 — 화면 안에서 바뀌지 않고, 범위를 바꾸는 링크(랜딩의 「서울 상권 보기」)는 주소를 새로 연다.

## 2. 무엇이 고양·파주만 보이나

`lib/siteScope.ts` 가 11-10 의 「서울만」 상수를 **주소로 고르는 범위 둘**(`seoul` · `goyang-paju`)로 넓혔다. 화면·API 는 종전대로 그 파일의 함수로만 묻는다(`isSiteCity` · `isSiteRegion` · `isSiteSido` · `isSiteRankGroup` · `showsCrossRegion`).

| 자리 | 고양·파주 범위 |
|---|---|
| 상권 목록(`listDistricts`) · 상권 외곽선 | 고양·파주 서빙 26곳(고양 18 · 파주 8) |
| 업종 순위 | 경기 묶음의 고양·파주 줄만. **순위 숫자는 그대로**(경기 76곳 안의 순위라 번호가 건너뛴다 — 화면이 그렇게 말한다) |
| PPPP 네 트랙 · 레일 · 흐름(5판) | 서울과 같은 화면 그대로. 상권만 고양·파주 |
| 랜딩 | 「고양·파주 26개 상권」 · 「고양·파주만 제공」 · 「서울 상권 보기」 링크(`LANDING_HUBS_GOYANG_PAJU` — 백엔드 테스트가 서빙 거점 수와 대조) |
| 상권 흐름(파주 → 고양 → 서울) | **닫혀 있다** — 서울을 잇는 화면이라 「고양·파주만」 요청과 어긋난다 |

## 3. 하지 않은 것 · 알아둘 것

- 서울 순위 · 서울 모델 · 백엔드 서빙 목록 · 서울 기본 화면 — 바꾸지 않았다. 서울 기본 동작은 `siteScope.test.tsx` 와 PPPP 실화면 검사(22/22)가 지킨다.
- **같은 앱의 범위일 뿐 별도 배포·별도 도메인이 아니다.** 같은 번들·같은 백엔드를 쓴다.
- 고양·파주에는 서울 전용 자료가 없어 화면이 「서울만 제공」·「자료가 없어요」로 밝힌다(생활인구 시간대 · TRDAR 수요 · 본전 시점 · LSTM 공실 예측 `/ai/predict-vacancy` 404 는 설계다). 지어내지 않았다.
- 고양·파주 상권은 대부분 **공유 임대 앵커**(「*」)이고 다수가 「표본 소형」 문구를 단다.
- 한 번 정한 탭 범위는 sessionStorage 라 같은 탭에서 `/` 로 가도 고양·파주로 열린다 — 서울로 가려면 `?region=seoul`(랜딩 링크).

## 5. 다시 만지는 법

- 범위를 늘리려면 `lib/siteScope.ts` 의 `SCOPES` 에 한 줄 + 짧은 주소는 `app/main.py` 에 라우트 하나 + 랜딩 숫자(`landingFacts`) + 백엔드 `test_landing_facts` 의 도시 목록.
- 고양·파주 화면에서 서울을 잇는 상권 흐름을 열려면 `crossRegion` 을 켜고 `CorridorClosed` 가림을 푼다(별도 결정).
