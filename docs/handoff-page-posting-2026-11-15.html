1. 왜 바꾸나

개발자 모임 피드백(2026-11-15): Platform·Page 는 좋다. Posting·Program 으로 가면서 내용이 산으로 가고, 그 숫자가 「가설」이라 믿기 어렵다. 인테리어·오프라인 마케팅이 부동산 앱에 필요한가?

저장소 산출물로 확인한 원인은 셋입니다.

  1. 질문이 바뀐다. Platform·Page 는 「어디 · 몇 층」을 실측으로 답하는데, Posting 은 「고급화·가성비·기능중심 중 어느 전략」이라는 사업계획 질문으로 넘어간다. 업종이 정해진 창업자는 그렇게 생각하지 않는다.
  2. 결론 숫자가 추정 네 겹이다. 회수기간 = R-ONE 지역 평균 임대료 × 상권·업종 평균 추정매출 × 면적 비례 × 손으로 적은 투자비 계수. 그래서 추천 전략의 회수가 1개월 미만인 유닛이 891 중 296(2026-10-28)이고, 화면이 그 자리들에 「한 달 안에 본전」이라고 말한다.
  3. 자리 사실과 사업계획이 한 화면에 섞였다. Posting 7쪽 중 「주변 업종 지도」「찾아오는 길」은 Page 성격의 자리 사실이다.

방향 — 예측을 줄이고 확인을 늘린다. 숫자는 실측·공식 통계·사용자가 들은 금액 위에 세우고, 그 위에서 계산만 한다. 「얼마 벌까」 대신 「이 조건이면 얼마나 팔아야 하나」, 「이 층이 비었다」 다음에 「내 업종이 들어갈 수 있나」.

2. 바뀌는 네 질문 결정 ② 승인 · 11-15

트랙지금바뀐 질문담당
Platform이 입지는 어떤 플랫폼인가현행 문구 유지 11-15 결정 — 승인안 「이 상권은 내 업종에 맞나 — 결과(개업 뒤 생존)로 검증한 순위」는 전방 검증에서 실력 판정이 나온 뒤 옮김(첫 계산이 구분불가)본 작업
Page어디에 page 자리가 있나어느 층이 비었고, 내 업종이 들어갈 수 있나팀원
Posting어떤 가격대로 posting 할까이 층 조건이면 얼마에 몇 개를 팔아야 하나팀원
Program누구와 잇고 어떻게 알릴까계약 전에 어떻게 작게 확인하나(답사·팝업 판정)본 작업

Price→Posting · Promotion→Program 대응은 유지됩니다. 네 트랙 화면·레일·진입로는 그대로 둡니다(아래 공통 규칙). 문구는 결정 ②로 확정됐습니다(2026-11-15). 화면·문서 문구는 트랙별 구현 PR 이 옮깁니다 — Page·Posting 행과 랜딩 문구는 팀원 PR 에서.

정체성 문장 개정본: 「업종이 정해진 예비창업자와, 업종을 바꾸거나 상권을 옮기려는 사업자가 계약하기 전에 어느 상권이 내 업종에 맞는지 · 어느 건물 몇 층이 비었고 그 층에 내 업종이 들어갈 수 있는지 · 그 조건이면 얼마나 팔아야 하는지 · 계약 전에 작게 확인하는 방법까지 본다.」 (결정 기록: docs/decision-confirm-before-contract-2026-11-15.md)

5. 2단계 · Page — 「이 빈 층에 내 업종이 들어갈 수 있나」

팀원

목표: 비었다 → 들어갈 수 있나(대장 기준)까지

왜 이 기능인가 — 창업자가 실제로 돈을 잃는 지점은 「계약했는데 영업신고가 막힘」이다. 인테리어보다 앞선 질문이고, 법령·공식 대장으로 답하니 가설이 아니다. 서울 빈 층 14,520곳 중 7,548곳(52%)의 대장 세부용도가 1종 근린생활시설 계열이다 — 일반음식점을 내려면 대장 기재 변경과 정화조·주차 요건 확인이 필요한 쪽. 2종 계열은 5,655곳(39%). (2026-11-15 실측 · 세부용도 키워드 분류라 근사값)

11-15 진행 — 이미 된 것(PR #238 · main 46e1e92): 2-C 사전등록 docs/prereg-floor-use-check-2026-11-15.md(채점 전) · 2-D 재료(data/collectors/eum_landuse.py 수집 → data/pipelines/build_use_check_inputs.py → data/gold/page_use_check_inputs.json) · 판정 서비스 apps/backend/app/services/use_check.py(schemas/use_check.py 의 다섯 갈래 ledger_ok · needs_check · use_change_needed · zoning_prohibited · missing_inputs). 면적 기준은 손으로 적지 않고 토지이음 응답의 별표1 정의에서 읽습니다. 서울 행위제한 수집은 21/24구까지 — 남은 곳은 토지이음 일일 한도(약 1,000콜) 때문에 이어서 받습니다. 자세한 것은 docs/finding-eum-landuse-2026-11-15.md.

그래서 2단계는 2-A(자리 사실 이동)와 2-E(화면 연결)부터입니다. 2-E 는 후보 조회(#240 머지됨) 위에서 — 그 응답의 regulation_status 를 위 다섯 갈래로 채웁니다.

8. 공통 규칙 · 완료 판정

⛔ PPPP 화면 보존(절대 규칙) — 네 트랙 구현 화면(Platform PlatformConsole · Page MapShell · Posting PostingConsole · Program CampaignStudio), 지도 탐색 레일, 흐름의 「지도」 진입로(늘 #/explore), 랜딩 네 질문(#how)은 빼거나 숨기거나 다른 화면으로 돌리지 않는다. 가드 apps/frontend/src/ppppScreens.test.tsx 를 skip·수정하지 않는다. 트랙 안의 쪽·탭 정리와 질문 문구 변경은 대상이 아니다(가드는 트랙 이름·순서를 본다).

  • 브랜치 feat/* · PR 은 작게. main 머지 → CI 전부 통과 뒤 Cloud Run 자동 배포. 새 alembic 리비전이 생기면 Neon 마이그레이션은 따로(수동).
  • 완료 판정은 실행 결과로 — 변경 파일 목록 + /verify 정적 3종(backend pytest · frontend build·lint·vitest · data/tests) + Posting·Page·랜딩·레일을 건드렸으면 py -3.11 scripts/pppp_screens_check.py + 바뀐 API 의 실제 응답. 못 돌린 단계는 「미실행」으로 적는다.
  • KPI 네 규칙 — 임계값 단독 금지(같은 표본의 무정보 기준과의 차이) · n 과 신뢰구간 동반 · 고르는 데 쓴 표본으로 보고 금지 · 계측기 없는 목표는 KPI 가 아니다. 사전등록 → 계산 → 보고 순서, 결과를 본 뒤 기준을 바꾸지 않는다.
  • 숫자 표기 — 근거 배지 필수. 층 계수를 곱한 임대료를 「이 층 월세」라 쓰지 않는다. 「입점 가능」「허가됨」 단정 금지. 재료가 없으면 「자료 부족」(지어내지 않는다).
  • 비밀값 — 키 값을 출력·커밋하지 않는다. data/.env 는 스크립트가 읽게 한다.
  • 숫자 인용은 문서가 아니라 python scripts/pppp_status.py · python scripts/kpi_baseline.py 출력으로.
  • 코드 규칙 — 응답·주석·문서 한국어(기술 용어 영문 병기) · FastAPI 라우터는 app/api/v1/, 로직은 app/services/, 스키마 app/schemas/ · 프론트 API 호출은 src/lib/api.ts 로 · @/ 별칭 · 스타일은 CSS 변수(src/styles/tokens.css) — tailwind 를 들이지 않는다.
