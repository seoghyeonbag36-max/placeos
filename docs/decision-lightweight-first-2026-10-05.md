## 1. 로그인 — 구글 로그인 (사용자 결정 2026-10-05)

### 왜 구글인가

| 대안 | 사람이 할 일 | 스키마 | 판단 |
|---|---|---|---|
| **구글** | 이미 쓰는 GCP 프로젝트에 OAuth 클라이언트 ID 하나. 비밀(secret) 없음 | **그대로** — 구글이 소유를 확인한 이메일을 준다 | ✅ 채택 |
| 카카오 | 카카오 개발자 앱 등록. 이메일을 받으려면 비즈 앱 전환 | 이메일 없이 받으면 새 컬럼 → Neon 마이그레이션 수동 적용 | 필요해질 때 |
| 이메일 매직링크 | 메일 발송 계정(Gmail 앱 비밀번호 등) | 그대로 | 링크가 스팸함으로 갈 수 있다 |

스키마가 그대로라는 것이 결정적이다 — 10-04 에 마이그레이션 두 건이 배포보다 늦어 로그인한
요청이 전부 500 이었다(`docs/deploy-cloud-run.md` §2026-10-04). 이번 변경은 **마이그레이션 0건**이다.
비밀번호가 없는 계정은 해시 자리에 `!` 를 넣는다(bcrypt 해시는 `$` 로 시작하므로 겹치지 않고,
어떤 입력과도 일치하지 않는다 — `core/security.UNUSABLE_PASSWORD`).

### 어떻게 도나

```
브라우저 ── 구글 버튼(GIS) ──▶ 구글 ── 서명된 ID 토큰 ──▶ 브라우저
브라우저 ── POST /api/v1/auth/google {credential, org_name?} ──▶ 서버
서버: 구글 공개키(JWKS)로 서명 · aud(=우리 클라이언트 ID) · iss · exp · email_verified 확인
      → 처음이면 가입(조직 = 적은 사업 이름, 없으면 「내 작업 공간」) → 우리 JWT
```

- **꺼져 있으면 흔적이 없다.** `GOOGLE_CLIENT_ID` 가 비면 `/auth/providers` 가 `null` 을 주고 화면에
  버튼이 없으며 `/auth/google` 은 404 다. 머지 직후(10-05)에는 꺼진 채였고, **같은 날 클라이언트 ID 를
  넣어 켰다**(`/auth/providers` 가 ID 를 돌려주는 것을 확인). 구글 콘솔의 게시 상태는 「테스트 중」이라
  **테스트 사용자로 등록한 계정만** 로그인된다 — 일반 사용자에게 열려면 아래 「켜는 법」 1단계를 마쳐야 한다.
- 받는 것은 **이메일 하나**다. 토큰에 실려 오는 이름·사진은 꺼내지 않는다.
- 첫 화면(`pages/Home.tsx`)이 `/auth/providers` 를 한 번 묻고 로그인·가입 화면에 넘긴다. 못 물으면
  (서버 다운·옛 서버) 이메일 폼만 그린다 — 들어올 길이 사라지지 않게.

### 선점 차단 — 비밀번호 가입은 이메일을 확인하지 않았다

남이 먼저 내 주소로 비밀번호 가입을 해 둘 수 있다. 그 상태에서 진짜 주인이 구글로 들어오면:

1. 그 계정으로 들어가되 **비밀번호를 끊는다**(`!`) — 감사로그 `auth.google_link`.
2. 토큰에 실린 `cv`(로그인 수단 지문 = 서버 비밀로 HMAC 한 해시 앞 16자)가 바뀌어, 선점자가
   **이미 쥐고 있던 토큰도** 바로 무효가 된다(`core/security.credential_version`). 토큰 목록을
   저장하지 않고 그렇게 하는 방법이다.
3. `cv` 가 없는 옛 토큰(10-05 전 발급)은 통과시킨다 — 막으면 배포 순간 전원이 로그아웃되고,
   그 토큰들도 7일 안에 저절로 끝난다.

### 만들지 않은 것

- **비밀번호 재설정 흐름.** 체크리스트가 짚은 바로 그 자리다. 잊었으면 같은 이메일의 구글 계정으로
  들어오면 된다(로그인 화면에 안내).
- **로그인 시도 제한.** Cloud Run 인스턴스마다 메모리가 달라 프로세스 안 카운터로는 약하다. 대신
  구글을 기본 경로로 돌려 비밀번호 표면 자체를 줄인다. 열린 항목으로 남긴다(§8).
- **비밀번호 가입을 닫지는 않았다.** 구글 계정이 없는 창업자의 입구이고, `[내부]` 시험 가입(curl) 절차도
  이것을 쓴다. 가입 화면에서는 「구글 계정 없이 이메일·비밀번호로 가입」 아래로 접었다.

### 켜는 법 — 사람 몫(약 5분)

> 콘솔 메뉴 이름은 2026-10 현재 **Google 인증 플랫폼**의 「개요 · 브랜딩 · 대상 · 클라이언트 · 데이터 액세스」다
> (예전 「OAuth 동의 화면」「사용자 인증 정보」에 해당). 처음이면 「개요 → 시작하기」 마법사가 앱 정보 → 대상 →
> 연락처 → 완료 순으로 묻는다.

1. **앱 설정과 게시.** 마법사에서 앱 이름 PlaceOS · 지원 이메일 · 대상 **외부**. 범위는 기본(openid·email·profile)뿐이라
   민감 범위 검수 대상이 아니다. 게시 상태 변경은 **대상 → 앱 게시**인데, **브랜딩의 필수 항목을 다 채우기 전에는
   버튼이 비활성**이다(10-05 실측 — 「앱을 게시하려면 브랜딩 페이지에서 구성을 완료해야 합니다」). 게시 전에는
   같은 화면의 **테스트 사용자**에 본인 구글 이메일을 넣으면 그 계정은 지금도 로그인된다(최대 100명).
   ⚠ 브랜딩이 개인정보처리방침 링크를 요구하면 §8 의 처리방침 페이지가 먼저 있어야 한다.
2. **클라이언트 → 클라이언트 만들기 → 웹 애플리케이션.** 승인된 JavaScript 원본:
   `https://placeos.web.app` · `http://localhost:5173` · `http://localhost`. 리디렉션 URI 는 필요 없다(팝업 흐름).
   원본이 빠지면 버튼은 뜨지만 누를 때 `origin_mismatch` 로 막힌다.
   ⚠ 클라이언트 ID 앞자리는 **프로젝트 번호**다. 10-05 에 만든 ID(`714790792235-…`)는 서버 프로젝트
   (`798830962560`)가 아니라 다른 프로젝트(My First Project)에 있다 — 로그인은 정상 동작한다(서버는 ID 값만
   확인한다). 나중에 찾기 쉽게 클라이언트 이름을 구분해 둔다.
3. Cloud Run 에 넣는다 — **`--update-env-vars`** 로(`--set-env-vars` 는 JWT_SECRET 등 다른 값을 날린다):
   ```powershell
   & "$env:LOCALAPPDATA\Google\Cloud SDK\google-cloud-sdk\bin\gcloud.ps1" run services update spaceos `
       --region=us-central1 --project=spaceos-digital-twin `
       --update-env-vars=GOOGLE_CLIENT_ID=<클라이언트 ID>
   ```
   배포 워크플로(`deploy.yml`)는 런타임 환경변수를 건드리지 않으므로 한 번 넣으면 남는다.
4. 확인: `curl.exe -s https://placeos.web.app/api/v1/auth/providers` → `{"google_client_id":"…"}`,
   첫 화면에 「Google 계정으로 계속하기」. 로컬은 `apps/backend/.env` 에 같은 줄.

## 2. 개인정보 — 최소화 · 안내 · 파기

### 받는 것(코드 기준)

| 표 | 칼럼 | 비고 |
|---|---|---|
| `users` | `email` · `hashed_password` | bcrypt. 구글 계정은 `!` |
| `orgs` | `name` | 사업 이름(구글 가입에서 비우면 「내 작업 공간」) |
| `business_workspaces` | `data` | 목적·업종·상권·사업 이름·설명(자유서술) |
| `pilot_feedback` | `nps_score` · `would_pay` · `comment` | KPI③ |
| `audit_log` | `action` · `detail` | 이용 기록은 경로, 가입·로그인은 **수단("password"·"google")만** |
| `revoked_tokens` | `token_hash` | 로그아웃한 토큰의 해시 |

### 바꾼 것

- **감사로그에 이메일 사본을 적지 않는다.** 가입·로그인 행의 `detail` 이 이메일이었다. 행마다 `user_id` 가
  있어 누가 했는지는 그것으로 충분하고, 사본은 탈퇴 때 지울 곳만 늘린다. 아무 코드도 그 값을 읽지 않았다.
- **탈퇴(`DELETE /api/v1/auth/me`) = 즉시 파기.** 계정 화면 맨 아래 「회원 탈퇴」 → 확인 → 삭제.

  | 경우 | 지우는 것 | 남는 것 |
  |---|---|---|
  | 혼자 쓰던 조직 | 사용자 · 조직 · API 키 · 사업 정보 · 피드백 · 감사로그 전부 | 없음 |
  | 다른 멤버가 있는 조직 | 사용자 · 멤버십 · 사업 정보 · 본인 피드백 | 조직과 남은 멤버. 떠난 사람의 감사 행은 `user_id` 를 비운 **익명 집계**로만(조직 사용량이 과거로 거슬러 줄지 않게). 옛 가입·로그인 행의 이메일 사본도 이때 비운다 |

  순서는 외래키 방향(자식 → 부모)이다. 테스트가 SQLite 외래키를 켜고 같은 순서를 강제한다
  (`tests/test_auth_account_delete.py` — 순서가 틀리면 Postgres 처럼 `IntegrityError` 로 운다).
- **수집 안내.** 가입 화면(과 구글이 켜진 로그인 화면 — 처음 온 사람은 거기서도 가입된다)에 한 단락
  (`components/PrivacyNote.tsx`). 문구는 코드가 실제로 하는 일과 같아야 하므로, 저장·파기 코드를
  바꾸면 그 파일 머리말대로 함께 고친다.

## 3. 결제 — PG 를 붙이지 않는다

- **지운 것.** `apps/backend/app/api/v1/payments.py` — `router.py`·`main.py` 어디에도 등록되지 않아 서빙에
  닿은 적이 없다. 그런데 파일이 있으면 "결제가 있다"로 읽히고, `docs/VIBE-PROMPTS.md` 가 그 스텁을
  "실제 네이버페이 결제형 플로우로 채워줘"라고 지시하고 있었다. 체크리스트가 경고한 바로 그 일을
  다음 세션에 시키는 문장이다. `apps/frontend/src/design/components/NaverPayButton.tsx` 도 함께 지웠다
  (import 0건 · Tailwind 클래스뿐이라 렌더돼도 스타일이 없었다).
- **가는 길(순서).**
  1. **사전 예약 = 결제 의향** — 이미 계측 중이다(KPI③ `would_pay`, `POST /api/v1/feedback`).
  2. 계약이 생기면 **수동 계좌이체 + 세금계산서**. B2B 월 구독(DaaS)은 카드 PG 보다 이쪽이 관행이다.
  3. 정기결제 PG 는 **수동 정산이 실제 병목이 됐을 때** — 그때의 건수를 기록하고 결정한다.
- 08-26 결정 2(무상 파일럿 · 과금 3순위)는 그대로다. 그 문서(§4-3)의 "네이버페이 스텁을 실제 연동으로"
  한 줄만 이 문서로 정정했다.

## 4. 앱 — 웹앱(PWA) 먼저

- **더한 것.** `apps/frontend/public/manifest.webmanifest` · 아이콘 4종(`public/icons/` — 안드로이드 192·512 ·

## 5. 지도 — SDK 는 유지, 실패해도 길은 남긴다

- **유지하는 이유.** 체크리스트의 대안("주소를 텍스트로 받고 지도 앱 링크로")은 지도가 부가 기능인
  서비스의 이야기다. PlaceOS 에서는 공실 히트맵·층 스택·거리뷰가 Page 트랙의 본체다.
- **바꾼 것.**
  - `components/MapHost.tsx` — 실패 문구의 첫 줄을 사용자에게: "왼쪽 패널의 목록과 수치는 그대로 볼 수 있고,
    건물을 고르면 그 자리를 카카오맵에서 열 수 있다". NCP 콘솔 안내는 「원인(운영자용)」으로 접었다.
  - `components/BuildingViewer.tsx` — 건물 아래 **카카오맵 위치 · 로드뷰 링크**(`lib/externalMap.ts`).
    키가 필요 없어 SDK 가 한도 초과·도메인 미등록·차단으로 안 떠도 돈다. 거리뷰가 없거나 실패한
    자리에서는 그 링크로 안내한다.
- **네이버 링크를 쓰지 않은 이유.** 좌표로 여는 웹 링크 형식이 공식 문서에 있는 것은 카카오뿐이다
  ([카카오 지도 URL](https://apis.map.kakao.com/web/guide/) — `/link/map/{이름},{위도},{경도}` ·
  `/link/roadview/{위도},{경도}`). 네이버는 앱 스킴(`nmap://`)만 공개돼 있고 데스크톱에서는 앱 설치 화면으로
  간다([NCP URL Scheme](https://guide.ncloud-docs.com/docs/maps-url-scheme)). 문서에 없는 주소 형식을
  추측해 박아 두면 바뀌는 날 조용히 깨진다.

## 6. 알림 · 본인인증 — 만들지 않았고, 지금은 만들지 않는다

- **알림이 필요해지면** 이메일(구글 로그인으로 확인된 주소) → 웹 푸시(iOS 는 홈 화면 추가가 전제 — §4 가
  그 전제다) → 알림톡은 마지막.
- **본인인증**은 성인 확인처럼 법이 요구할 때만. 지금 PlaceOS 에는 그런 기능이 없다.

## 7. Program — 창업자에게 내주는 검증 program 에도 같은 원칙

`services/marketing.py` 의 LLM 시스템 프롬프트(원칙 절)에 한 항목을 더했다: 검증 도구는 오늘 바로 쓸 수
있는 가장 가벼운 것(신청 폼·계좌이체 송금 QR·사전 예약·오픈채팅·이메일)으로 고르고, 앱 출시·PG 연동·
알림톡·본인인증·회원가입 시스템을 검증 단계에서 제안하지 않는다. MVP 지표는 이미 "사전 예약·사전주문
전환율"이다(`_MODE_SIGNAL["mvp"]`) — 규칙이 그 지표와 같은 방향을 가리키게 맞춘 것이다.
