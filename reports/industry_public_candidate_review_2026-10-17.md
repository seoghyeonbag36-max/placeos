# 업종 공공자료 원천 재조회·건물 주소 후보 검증

## 원천 손상 재조회

2026-10-17 서울 열린데이터광장 API에서 기존 손상 표본을 다시 받았다.
응답 바이트를 새 Bronze 디렉터리에 보존하고 SHA-256을 보고서에 기록했다.
기존 원본·Silver·Gold는 변경하지 않았다. 외부 원천 재조회이며 합성값은 쓰지 않았다.

- 음식점: 관리번호 `3200000-101-1989-02013`, 인허가일자 `1989-11-10`로 조회한 34행에서
  동일한 개방자치단체코드·관리번호 1행 확인. 상호/주소 연결 필드의 U+FFFD 손상이 남아 있다.
- 유흥주점: 관리번호 `3220000-102-1998-04375`, 인접 1,000행 재조회에서 동일 식별키 1행 확인.
  연결 필드 손상이 남아 있다.
- 새 응답은 엄격한 UTF-8 디코딩을 통과했다. 두 표본은 현재 API 자체가 대체문자를 반환한다.
  모든 손상 행이 같은 원인이라는 뜻은 아니다. 정상 문자열을 확보한 것으로 판정하지 않는다.

API 행 번호가 바뀌어 기존 위치만 재조회하면 다른 행을 받았다. `MGTNO`는 출력 필드로,
이를 쿼리 필터로 시험한 호출은 전체 총량을 반환해 무효였다. 그 결과는 신원 부재의 증거가 아니다.
공식 요청인자는 `APVPERMYMD`·`TRDSTATEGBN`·`BPLCNM`이다.
출처: [서울시 일반음식점 인허가 공식 명세](https://data.seoul.go.kr/dataList/OA-16094/S/1/datasetView.do?tab=A).
인허가일자 위치 인자로 재시도하여 음식점의 동일 관리번호를 확인했다.

근거: `industry_public_source_permit_date_probe_2026-10-17.json`,
`industry_public_source_window_probe_2026-10-17.json`.

## 건물 주소 후보 계약

신규 `data/validation/industry_public_candidates.py`는 진단 전용이다.
이름은 공백만 정리하고, 인허가 주소의 쉼표·괄호 전 건물 주소가 상가정보 주소와 같은 행을 후보로 둔다.
원문·파일 위치·원천 식별키·파일 해시를 보존하며 항상 최상위 `store_id=null`이다.
아래 상태는 매칭 성공이 아니다.

- 손상 문자열: 후보를 만들지 않고 `blocked_corrupted_text`.
- 이름·주소 결측: `missing_name_or_address`.
- 복수 점포 후보: 층이 같은 후보가 있더라도 하나를 선택하지 않는다.
- 명시적인 단일 층만 비교한다. 호실번호로 층을 추정하지 않고, 복수 층·층 범위·해석 불능은 `unknown`.
- 층 일치도 확정 증거가 아니다. 호실 비교와 실제 동일 점포 검증은 하지 않았다.
- 같은 점포 ID를 여러 인허가가 주장하면 별도 집계한다. 휴폐업 포함 역사 자료라 동시 충돌로 단정하지 않는다.

## 실측 결과

입력은 2026-10-09 기존 Bronze의 서빙 거점 점포와 인허가 10종이다.
인허가 715,645행 중 단일 점포 후보 32,892행, 복수 점포 후보 514행.
후보 점포쌍 33,937개 중 명시 층 일치 14,876쌍, 불일치 2,497쌍, 확인 불가 16,564쌍이다.
복수 인허가의 후보가 된 점포 ID는 1,280개다. 문자 손상 연결 필드는 233행에서 발견됐다.
각 수치는 원천 행·후보쌍·점포 ID의 서로 다른 단위이므로 더해 점포 수로 읽지 않는다.
업종별 집계·실제 예시·해시는 `industry_public_candidate_conflicts_2026-10-17.json`에 있다.

현실적인 후속은 제공기관의 정상 원문 확보, 또는 손상 행 격리·부분 승격을 허용할지에 대한 명시적인 계약 결정이다.
후자는 기존의 전체 승격 실패 정책을 바꾸므로 이번 작업에서 임의 적용하지 않았다.
건물 후보 역시 원문 문자열을 지우거나 확정 조인으로 승격하지 않았다.
